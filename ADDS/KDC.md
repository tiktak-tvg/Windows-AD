### Kerberos Key Distribution Center (KDC) — это центральный компонент протокола аутентификации Kerberos, используемый в Active Directory и других системах для безопасной аутентификации пользователей и служб в распределённой сети. 
Его основная задача — выдавать билеты (tickets), которые доказывают личность без передачи паролей по сети.
***
Основные роли KDC:
Центр распространения ключей (KDC):

Служба аутентификации (Authentication Service — AS) — проверяет первоначальные учётные данные и выдаёт TGT.

Служба выдачи билетов (Ticket-Granting Service — TGS) — выдаёт билеты для доступа к конкретным сетевым службам.

База данных ключей:

Хранит секретные ключи (хэши паролей) всех пользователей и служб (компьютеров, принтеров, приложений).

В Active Directory эта база данных — часть NTDS.dit на контроллере домена.

Как работает KDC (упрощённая схема):
Шаг 1: Получение TGT (билета для получения билетов)
Пользователь вводит логин/пароль на клиентском ПК.

Клиент вычисляет хэш пароля (это и есть секретный ключ пользователя).

Клиент отправляет запрос AS_REQ в KDC:
"Я пользователь Alice, хочу TGT".

KDC проверяет наличие Alice в базе, извлекает её секретный ключ (хэш пароля).

KDC создаёт TGT (Ticket-Granting Ticket), который содержит:

Идентификатор пользователя (SID, группы).

Срок действия (обычно 10 часов).

Сеансовый ключ (случайный симметричный ключ для общения между клиентом и TGS).

KDC шифрует TGT секретным ключом KDC (чтобы клиент не мог его подделать).

KDC отправляет ответ AS_REP, содержащий:

TGT (зашифрованный ключом KDC).

Сеансовый ключ (зашифрованный секретным ключом пользователя).

Клиент расшифровывает сеансовый ключ своим хэшем пароля.
Теперь у клиента есть TGT и сеансовый ключ для TGS.

Важно: Пароль никогда не передаётся по сети. Только хэш используется для шифрования/расшифровки.

Шаг 2: Получение билета доступа к службе
Клиент хочет получить доступ к службе (например, файловому серверу \\FS01).

Клиент отправляет TGS_REQ в KDC:

TGT (который зашифрован ключом KDC, поэтому клиент его не читает).

Аутентификатор (зашифрованный сеансовым ключом TGS) — доказывает, что у клиента есть сеансовый ключ.

Идентификатор целевой службы (HTTP/FS01).

KDC расшифровывает TGT своим секретным ключом, извлекает сеансовый ключ TGS.

KDC проверяет аутентификатор с помощью сеансового ключа.

KDC создаёт ST (Service Ticket) для доступа к \\FS01:

Идентификатор пользователя, группы.

Новый сеансовый ключ для службы (для общения между клиентом и \\FS01).

KDC отправляет TGS_REP, содержащий:

ST (зашифрованный секретным ключом службы \\FS01 — чтобы только служба могла его прочитать).

Сеансовый ключ для службы (зашифрованный сеансовым ключом TGS).

Клиент расшифровывает сеансовый ключ для службы (используя сеансовый ключ TGS).

Шаг 3: Доступ к службе
Клиент отправляет AP_REQ службе \\FS01:

ST (зашифрованный ключом службы).

Новый аутентификатор (зашифрованный сеансовым ключом для службы).

Служба \\FS01 расшифровывает ST своим секретным ключом (который известен ей и KDC).

Служба проверяет аутентификатор.

Если всё верно, служба предоставляет доступ.

Для взаимной аутентификации служба может отправить подтверждение клиенту (AP_REP).

Ключевые элементы Kerberos:
TGT (Ticket-Granting Ticket) — билет для получения других билетов, не даёт прямого доступа к службам.

ST (Service Ticket) — билет для доступа к конкретной службе.

Сеансовый ключ (Session Key) — временный симметричный ключ, генерируемый KDC для защиты общения между двумя сторонами.

Секретный ключ (Secret Key) — длительный ключ, основанный на пароле (для пользователя) или машине (для службы).

Аутентификатор (Authenticator) — метка времени, зашифрованная сеансовым ключом, доказывает свежесть запроса.

Интеграция с Active Directory:
KDC работает на каждом контроллере домена как часть службы lsass.exe.

База данных ключей — это учётные записи Active Directory (атрибуты unicodePwd, supplementalCredentials).

Имена служб в AD — это SPN (Service Principal Name), например HTTP/webapp.contoso.com.

Регистрация SPN выполняется автоматически при присоединении компьютера к домену или вручную для служб.

Преимущества Kerberos в AD:
Взаимная аутентификация — клиент и служба могут убедиться в подлинности друг друга.

Делегирование (Kerberos Delegation) — служба может действовать от имени пользователя при доступе к другим службам.

Отсутствие передачи паролей по сети.

Поддержка одноразовой аутентификации (SSO) — пользователь вводит пароль один раз при входе в систему.

Защита от replay-атак — аутентификаторы содержат метки времени.

Пример типичного потока в Windows:
text
Пользователь (Alice) → Входит в ПК (WinLogon) → LSA → Kerberos-клиент → 
1. Запрос TGT → KDC на DC → TGT хранится в памяти (кеш LSA).
2. При обращении к \\FS01 → Запрос ST → KDC → Получение ST.
3. Отправка ST в \\FS01 → Доступ к файлам.
Проблемы и уязвимости Kerberos:
Золотой билет (Golden Ticket) — если злоумышленник украдет ключ KDC (krbtgt), он может создать любой TGT.

Серебряный билет (Silver Ticket) — если украден ключ службы, можно создать поддельный ST (но без TGT).

Атаки на спуфинг SPN — перенаправление запросов на злоумышленника.

Необходимость синхронизации времени (протокол чувствителен к расхождению времени, обычно ±5 минут).

Сравнение с NTLM (старый протокол Windows):
Параметр	Kerberos	NTLM
Безопасность	Выше (нет передачи хэша)	Ниже (передача хэша)
Скорость	Быстрее (билеты кешируются)	Медленнее (запрос к DC каждый раз)
Делегирование	Поддерживается	Нет
Сквозная аутентификация	Да	Нет
Требует доступа к DC	Только для получения TGT	Для каждой аутентификации
Важно в современных сетях:
Kerberos — основной протокол аутентификации в Active Directory с Windows 2000 и выше.

NTLM сохраняется для обратной совместимости (например, недоменные сценарии).



Windows постепенно отказывается от NTLM в пользу Kerberos (политика безопасности).
